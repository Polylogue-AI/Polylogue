# 接口契约 v0.5

前端（Claude 负责）和后端（ChatGPT 负责）之间唯一的约定。**双方都只按这份文档写代码**。

- 想改契约：先改这份文档并把版本号加 0.1，在"变更记录"写一行，再改代码。
- 前端的 TypeScript 类型定义在 `frontend/src/api/types.ts`，和本文档逐字段对应。两者冲突时以本文档为准，并修正另一方。
- 前端自带一个模拟后端（`frontend/src/api/mock.ts`），行为就是本契约的参考实现。后端遇到描述不清的地方，可以看它是怎么做的。

## 0. 通用约定

| 项目 | 约定 |
|---|---|
| 基础路径 | REST 为 `/api/...`，WebSocket 为 `/ws/...`。开发时前端 Vite 把这两个前缀代理到 `http://localhost:8000` |
| 鉴权 | 登录后后端设置 HttpOnly Cookie `rt_session`。REST 和 WebSocket 都靠这个 Cookie 识别用户。未登录返回 `401` |
| 格式 | JSON，UTF-8，字段名用 `snake_case` |
| ID | 字符串。建议带前缀：用户 `u_`、AI 成员 `ai_`、房间 `r_`、消息 `m_`、任务 `t_` |
| 时间 | ISO 8601 字符串，带时区，例如 `2026-11-22T20:15:00+08:00` |
| 金额 | 人民币元，`number`，保留 4 位小数。LiteLLM 算出的是美元，后端用配置里的汇率 `USD_CNY_RATE` 换算。界面会标注"预估" |
| 错误 | HTTP 4xx/5xx，响应体 `{"error": {"code": "budget_exceeded", "message": "给人看的中文说明"}}` |
| 假模型模式 | 设置环境变量 `LLM_MODE=fake` 时，后端不需要任何 API Key 就能启动，所有模型调用由 `FakeLLM` 完成（逐字输出、有费用、有延迟）。其余行为与真实模式完全一致。前端对接和自动化测试都用这个模式 |

## 1. 数据类型

```ts
type Mode = 'round' | 'pipe' | 'cross' | 'debate'

// 登录的人
interface User {
  id: string
  name: string            // 桌上显示的名字
  short: string           // 头像上的字，1–2 个字符
  color: string           // 头像底色，如 "#FFD8A8"
  is_admin: boolean
  monthly_limit_cny: number | null
}

// 一个 AI 成员（模型 + 角色设定）
interface AiMember {
  id: string
  name: string            // "Claude"、"唱反调的 DeepSeek"
  short: string
  color: string
  model: string           // LiteLLM 的模型名，如 "anthropic/claude-sonnet-5-5"
  role: string            // 简短角色名，如 "唱反调"
  system_prompt: string
  temperature: number     // 0–1
  max_chars: number | null       // 每次发言字数上限，null 表示不限
  monthly_budget_cny: number | null
  can_mention: boolean    // 是否允许它主动 @ 其他模型（M3）
  month_cost_cny: number  // 只读：本月已花费
}

// 可选模型，由后端根据已配置的 API Key 返回
interface ModelOption {
  id: string              // LiteLLM 模型名
  label: string           // 给人看的名字
  provider: string        // "anthropic" | "openai" | "gemini" | "deepseek" | "dashscope" | "ollama" ...
  available: boolean      // Key 是否配置且最近一次检测可用
  supports_temperature: boolean  // 该模型是否接受 temperature 参数。false 时前端禁用温度滑杆
}

// 房间里的一个座位
interface Seat {
  id: string              // User.id 或 AiMember.id
  kind: 'human' | 'ai'
  name: string
  short: string
  color: string
  duty: Duty | null       // 本房间里的职责，人为 null
  role: string | null     // AI 的角色名（来自 AiMember.role），人为 null
}

type Duty =
  | 'speaker' | 'summarizer'                 // 圆桌
  | 'planner' | 'executor' | 'reviewer'      // 流水线（汇总由 planner 兼任）
  | 'answerer' | 'judge'                     // 交叉验证（judge 即主席）
  | 'pro' | 'con'                            // 辩论（judge 复用上面的值）

type RoomStatus =
  | 'idle'              // 已创建，未开始
  | 'running'
  | 'paused'            // 人点了暂停或打断，编排循环在等待
  | 'finished'          // 正常结束
  | 'budget_exceeded'   // 预算用完自动停止
  | 'error'             // 不可恢复的错误（如所有模型都调用失败）

interface RoomSummary {
  id: string
  title: string
  mode: Mode
  status: RoomStatus
  seats: Seat[]
  last_preview: string    // 最后一条消息的前 60 个字，格式 "Gemini：……"
  updated_at: string
  cost_cny: number
  budget_cny: number
  created_by: string      // User.id，费用记在此人名下
}

interface Room extends RoomSummary {
  topic: string           // 创建时输入的完整问题
  rounds: number          // 圆桌、辩论的轮数；流水线为最大返工次数；交叉验证忽略
}

interface RoomState {
  status: RoomStatus
  round: number                   // 当前第几轮，从 1 开始；未开始为 0
  total_rounds: number
  speaker_id: string | null       // 正在发言的成员
  next_speaker_id: string | null  // 预计下一位，给界面显示用，可以为 null
  cost_cny: number
  budget_cny: number
  context_tokens: number          // 下一次调用预计的输入 tokens
  summarized_until_round: number  // 第几轮及以前已被压缩成摘要，0 表示没有
  mode_state: ModeState
}

interface ModeState {
  // 流水线
  tasks?: PipeTask[]
  // 交叉验证
  phase?: 'answer' | 'review' | 'verdict' | 'done'
  // 辩论：裁判给正方的倾向分，0–100；还没评分时为 null
  score_pro?: number | null
}

interface PipeTask {
  id: string
  stage: 'plan' | 'exec' | 'review' | 'merge'
  title: string
  assignee_id: string
  status: 'queued' | 'running' | 'done' | 'needs_fix'
  rework_count: number
}

type MessageKind =
  | 'chat'      // 普通发言（人或 AI）
  | 'summary'   // 圆桌汇总者的结论
  | 'verdict'   // 交叉验证主席、辩论裁判的结论
  | 'steer'     // 人发出的"方向指示"，加入后续所有 AI 的上下文
  | 'system'    // 系统提示，如"预算已用完"

interface Message {
  id: string
  seq: number               // 房间内单调递增，从 1 开始。断线重连靠它补消息
  room_id: string
  author_id: string | null  // system 消息为 null
  kind: MessageKind
  content: string           // Markdown。前端用 react-markdown 渲染，不渲染原始 HTML
  round: number
  created_at: string
  mentions: string[]        // 被 @ 的成员 ID
  reply_to: string | null   // 回复的消息 ID
  cost_cny: number | null   // AI 消息才有
  interrupted: boolean      // 被人打断
  streaming: boolean        // 还在输出中（只出现在 snapshot 里）
  meta: MessageMeta
}

interface MessageMeta {
  task_id?: string                          // 流水线：属于哪个任务
  verdict?: 'approved' | 'needs_fix'        // 流水线：审查结论
  phase?: 'answer' | 'review' | 'verdict'   // 交叉验证
  anon_label?: string                       // 交叉验证互评时的匿名代号，如 "回答 A"
  side?: 'pro' | 'con' | 'judge'            // 辩论
  agreements?: string[]                     // 交叉验证主席：共识点
  disagreements?: string[]                  // 交叉验证主席：分歧点
}
```

## 2. REST 接口

### 登录

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| POST | `/api/auth/login` | `{invite_code: string, name: string}` | `User`，并设置 Cookie。邀请码大小写不敏感 |
| GET | `/api/auth/me` | — | `User`，未登录 `401` |
| POST | `/api/auth/logout` | — | `204` |

邀请码规则：
- 格式：6 位，字符取自 `A–Z` 和 `2–9`，去掉容易看错的 `O`、`I`。比较时不区分大小写。
- 管理员的邀请码在 `.env` 里配置（`ADMIN_INVITE_CODE`），用它登录的人 `is_admin = true`。
- 其余邀请码由管理员生成，7 天内有效，只能绑定一个人。
- 邀请码第一次使用时绑定到登录的名字。之后用同一个邀请码加**相同名字**登录，视为同一个人重新登录，不受 7 天限制。用同一个邀请码加不同名字登录，返回 `400 invite_used`。
- 会话 Cookie 有效期 30 天。

### 邀请码管理（仅管理员，非管理员返回 `403`）

```ts
interface Invite {
  code: string
  note: string            // 管理员填的备注，如"给小雨"
  created_at: string
  expires_at: string
  used_by: string | null  // 绑定的 User.id，未使用为 null
}
```

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/invites` | `Invite[]`，按 `created_at` 倒序 |
| POST | `/api/invites` | 请求体 `{note: string}`。返回新的 `Invite` |
| DELETE | `/api/invites/{code}` | 作废一个**未使用**的邀请码，`204`。已使用的返回 `400 invite_used` |

### 成员与模型

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/users` | `User[]`，团队里所有人 |
| GET | `/api/models` | `ModelOption[]` |
| GET | `/api/members` | `AiMember[]` |
| POST | `/api/members` | 请求体为 `AiMember` 去掉 `id`、`month_cost_cny`。返回 `AiMember` |
| PATCH | `/api/members/{id}` | 请求体为部分字段。返回 `AiMember` |
| DELETE | `/api/members/{id}` | `204`。已在房间里的成员保留历史消息 |

`POST`、`PATCH`、`DELETE /api/members` 只有管理员可以调用，其他人返回 `403`。

`GET /api/models` 的 `available`：真实模式下表示这家服务商的 Key 已配置，且最近一次检测成功；假模型模式（见第 0 节）下全部为 `true`。

`GET /api/models` 返回的模型列表 = 后端内置列表 + `.env` 里 `EXTRA_MODELS` 追加的模型 + 现有成员正在用的模型（去重）。`EXTRA_MODELS` 的格式是逗号分隔的 `模型名=显示名`，例如 `EXTRA_MODELS=openai/gpt-6.1-sol=GPT-6.1 Sol,openai/gpt-6.1=GPT-6.1`；没写显示名时用模型名 `/` 后面的部分。

`AiMember.model` 可以是任意 `服务商/模型名` 格式的字符串，不要求在 `/api/models` 列表里。前端提供"手动输入模型名"，用于列表里没有的型号。

`supports_temperature`：不接受 temperature 的模型（目前已知 Claude 5.5 全系列，以及 OpenAI 的推理模型如 GPT-5 系列）为 `false`。不确定的模型为 `true`。为 `false` 时，后端调用该模型不传 temperature，成员的 `temperature` 字段照常保存，以便换回支持的模型时还能用。

### 房间

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/rooms` | `RoomSummary[]`，按 `updated_at` 倒序 |
| POST | `/api/rooms` | 创建房间，见下。返回 `Room`，状态为 `idle` |
| GET | `/api/rooms/{id}` | `Room` |
| DELETE | `/api/rooms/{id}` | `204`，只有创建者或管理员可以删 |

创建房间请求体：

```ts
{
  topic: string
  title?: string               // 不填则后端取 topic 前 30 个字
  mode: Mode
  ai_member_ids: string[]      // 至少 2 个
  human_user_ids: string[]     // 不含创建者自己，后端自动加入
  duties?: Record<string, Duty> // 不填或缺的，后端按下表自动分配
  rounds: number               // 1–6
  budget_cny: number
  auto_start: boolean          // true 则创建后立即开始
}
```

职责自动分配规则（按 `ai_member_ids` 的顺序）：

| 模式 | 规则 |
|---|---|
| round | 全部 `speaker`，最后一个兼任汇总者（座位上 duty 仍显示 `speaker`）。如果有人被显式指定为 `summarizer`，就由他汇总；他同样参与每一轮发言 |
| pipe | 第 1 个 `planner`，最后 1 个 `reviewer`，中间的 `executor`。只有 2 个时：第 1 个 planner 兼 reviewer，第 2 个 executor |
| cross | 最后 1 个 `judge`，其余 `answerer` |
| debate | 第 1 个 `pro`，第 2 个 `con`，最后 1 个 `judge`；第 4 个及以后交替加入正反方 |

校验失败返回 `400`，例如辩论模式少于 3 个 AI：`{"error":{"code":"invalid_duties","message":"辩论需要正方、反方和裁判至少各一位"}}`。

## 3. WebSocket：`/ws/rooms/{room_id}`

一个房间一条连接。所有在房间里的人都收到同样的事件。

### 3.1 连接流程

1. 前端连接，后端用 Cookie 验证身份，失败则以 code `4401` 关闭。房间不存在则 `4404`。
2. 前端立即发 `{"type":"hello","last_seq":N}`。第一次进入时 `N = 0`。
3. 后端回复一条 `snapshot`：包含 `seq > N` 的全部消息、当前 `RoomState`、在线人员。**如果有消息正在输出，它也在里面，`streaming: true`，`content` 是目前已输出的部分**。
4. 之后后端推送实时事件。

断线后前端会自动重连。`last_seq` 是**从头数起、连续已完成的最大 `seq`**：遇到第一条还在输出的消息就停，取它前面一条的 `seq`。不能用收到的最大 `seq`，否则一条发言在断线期间结束，重连后就补不回它的全文。

后端照第 3 步补齐：`seq > last_seq` 的已完成消息，加上正在输出的那条（即使它的 `seq ≤ last_seq`）。前端按 `id` 去重，重复收到同一条消息没有问题。

### 3.2 前端 → 后端

```ts
type ClientEvent =
  | { type: 'hello', last_seq: number }
  | { type: 'say', content: string, mentions: string[], client_id: string }
  | { type: 'steer', content: string }   // 方向指示
  | { type: 'start' }      // idle → running；finished 后再发表示"再来一轮"
  | { type: 'pause' }      // 当前发言说完后暂停
  | { type: 'resume' }
  | { type: 'interrupt' }  // 立刻取消当前流式请求，保留已输出部分并标记 interrupted，然后进入 paused
  | { type: 'skip' }       // 同 interrupt，但不暂停，直接轮到下一位
```

`client_id` 是前端生成的临时 ID，后端在广播这条消息时原样放进 `message` 事件，前端据此把"发送中"的消息替换成正式消息。

### 3.3 后端 → 前端

```ts
type ServerEvent =
  | { type: 'snapshot', messages: Message[], state: RoomState, online: string[] }
  | { type: 'state', state: RoomState }     // 任何 RoomState 字段变化时，发完整的 state
  | { type: 'message', message: Message, client_id?: string }  // 一条完整的消息（人的发言、系统消息）
  | { type: 'message_start', message: Message }  // AI 开始发言，content 为空，streaming 为 true
  | { type: 'message_delta', id: string, delta: string }
  | { type: 'message_end', id: string, content: string, cost_cny: number | null, interrupted: boolean, meta?: MessageMeta }
  | { type: 'presence', online: string[] }  // User.id 列表
  | { type: 'error', code: string, message: string }  // 不断开连接的错误，前端弹提示
```

要求：
- `message_start` 时就分配好 `id` 和 `seq`。`message_end` 里的 `content` 是最终全文，前端用它覆盖拼接结果。
- `message_delta` 可以按 token 推，也可以攒 50ms 推一次，前端都能处理。
- 每次 `speaker_id`、`status`、`cost_cny`、`mode_state` 变化都要推 `state`。

### 3.4 编排行为（后端必须遵守，前端按这个展示）

| 情况 | 行为 |
|---|---|
| AI 正在输出时，人发了 `say` | 不打断当前输出。消息立即广播并入库；**下一位 AI 的上下文里必须先回应它** |
| `say` 里 @ 了某个 AI | 那个 AI 排到下一位。多个 @ 按 `mentions` 数组的顺序排，前端按 @ 在文字里出现的先后生成这个数组 |
| `pause` | 当前发言说完后停下，`status` 变为 `paused`，`speaker_id` 为 null |
| `interrupt` | 取消当前流式请求；已输出部分保留，`message_end.interrupted = true`；然后 `paused` |
| `skip` | 同上，但不暂停 |
| 并发阶段（流水线执行、交叉验证回答）收到 `interrupt` | 取消这一批里所有正在进行的调用，已输出部分保留并标记 `interrupted`，然后 `paused`。`resume` 后，被打断的调用**重新开始**（新消息、新 `seq`），已经完成的调用结果保留，这一批完整结束后才进入下一阶段 |
| 并发阶段收到 `skip` | 只取消 `speaker_id` 指向的那一个调用，不重做，这一批其余调用继续 |
| `steer` | 存为 `kind: 'steer'` 的消息并广播；之后每个 AI 的系统提示里都追加这段指示 |
| 发言前预算检查 | 房间已花费 ≥ 房间预算，或发起人本月已花费 ≥ 个人上限：发一条 system 消息说明原因，`status` 变为 `budget_exceeded` |
| 一个模型调用失败 | 重试 1 次；仍失败则发 system 消息"Gemini 调用失败，已跳过"，继续下一位 |
| 发言字数上限 | `max_chars` 写进提示词，`max_tokens` 兜底。**不截断**模型输出：`message_end.content` 必须等于已推送的全部 `message_delta` 拼起来的内容 |
| 同一房间 | 同时只允许一个编排任务。重复的 `start` 忽略 |
