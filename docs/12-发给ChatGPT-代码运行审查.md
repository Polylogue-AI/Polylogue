## 需要修改

### 1. 后端先于 Docker 启动时，沙箱一直不可用

`Sandbox.probe()` 只在启动时和 `failed()` 里调用。可是 `run()` 在 `available` 为 `false` 时会直接返回 `unavailable`，根本走不到 `failed()`。结果是：后端先启动、Docker Desktop 后启动（Windows 上很常见，Docker Desktop 开机启动得慢），沙箱会一直显示不可用，直到重启后端。

**改法**：沙箱不可用时，距离上次检测超过 30 秒就重新检测一次。`GET /api/sandbox` 和 `run()` 都会触发，并发请求只检测一次。补测试：先不可用，模拟 Docker 恢复后，再次调用变为可用。

### 2. "模型返回了空的流式响应"要区分两种情况

`orchestrator.py` 第 85 行把"没有内容也没有工具调用"和"`usage is None`"合在一起报同一个错误。实测时 GPT 有一次走到了这里，重试后成功，但日志里看不出是哪种情况。

**改法**：
- 两种情况分开报错，写清楚原因。
- 如果有内容或工具调用、只是缺少用量数据，不要当作失败重试（那样文字已经推送给前端，重试会再付一次钱）。改为用 `token_counter` 估算用量，并在日志里记一条警告。
- 补测试：`FakeLLM` 返回内容但不返回用量时，消息正常保存、有费用、不重试。

### 3. `GET /api/models` 要 5 秒，而且期间整个后端卡住

前端联调时发现，设置页的沙箱状态一直显示"检测中…"。实测 `/api/models` 每次要 5 秒左右。原因是 `LiteLLM.supports_tools` 调用 `litellm.supports_function_calling("ollama/llama3.1:8b")` 时，LiteLLM 会去连本机的 Ollama 服务（`localhost:11434`）查询模型信息。本机没装 Ollama，只能等超时，单这一项就约 3.3 秒，其他模型都在 0.2 秒以内。

更严重的是，`models` 是 `async` 接口，却在里面同步调用这些函数，阻塞了事件循环。这几秒里同一个后端的所有请求都卡住，包括 `/api/sandbox`、WebSocket 消息，以及正在进行的流式发言。

**改法**：
- `supports_tools` 的结果按模型名缓存，同一个模型只查一次。
- Ollama 模型不要调用会联网的 LiteLLM 函数，直接按规则表判断。不确定就返回 `false`，可以用你那个覆盖表打开。
- 接口里所有可能发起网络请求或很慢的同步调用（`supports_function_calling`、`validate_environment` 等）都放到线程里执行（`asyncio.to_thread`），或者在启动时预先算好。
- 补测试：`supports_function_calling` 被替换成会 sleep 的假函数时，第二次请求 `/api/models` 不再调用它；`/api/models` 进行中时，`/api/sandbox` 能立刻返回。

## 建议（可选）

### 4. 只有一个文件、又漏了 `path` 时，自动补上默认文件名

实测中两家各出现了一次工具参数错误，其中一次就是漏了 `path`。当 `files` 只有一项且缺少 `path` 时，可以按语言补默认名：`main.py`、`main.js`、`index.html`。多个文件时仍然报错。这样能少一次模型调用。如果你认为不应该放宽，就不做。
