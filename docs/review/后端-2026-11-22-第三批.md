## 必修

### 1. 并发阶段打断后点"继续"，房间直接进入 error

**复现**（Claude 本机的 `~/rt-e2e/repro_cross_interrupt.py`，不改后端代码，进程内运行）：交叉验证房间，4 个模型；在回答阶段收到几个 delta 后发 `interrupt`，状态变为 `paused`；再发 `resume`，最终状态是 `error`，`phase` 停在 `answer`。

**原因**：`interrupt` 取消了整批调用，每个 `call()` 都返回 `None`。`Crosscheck.run()` 拿到的回答全是空的，`anonymous` 为空，直接 `return False`。`run_room` 先 `await room.ready.wait()` 等用户点继续，用户点了之后才按 `success = False` 把状态设为 `error`。

流水线的执行阶段结构相同：不会进入 error，但所有任务的稿件都变成 `None`，审查被跳过，最后汇总出一份"无可用稿件"的结果，还标记为 `finished`。

**期望行为**（已写进契约 v0.4 第 3.4 节，项目负责人已确认）：并发阶段的 `interrupt` 等于"立刻暂停这一批"。已输出的部分保留并标记 `interrupted`；用户点继续后，**被打断的调用重新开始**，其他已完成的调用结果保留。`skip` 维持现在的行为，只取消当前一个发言者，不重做。

**要补的测试**：
- 交叉验证回答阶段 `interrupt` → `resume`：最终 `finished`，三份回答齐全（被打断的那份是重新生成的完整回答，旧的半截消息保留并标记 `interrupted`）。
- 流水线执行阶段同样的操作：每个任务都有完整稿件，且都经过审查。

## 建议本批顺手修

### 2. 需要 JSON 的步骤，提示词自相矛盾

规划、审查、互评、裁判打分这几步要求"仅返回 JSON"，但 `Turn.instruction` 会在后面固定追加"发言不超过 N 字""至少指出一个前面没人提到的问题或补充"。假模型发现不了这个问题；真实模型很容易在 JSON 前后多写一段解释，解析就会失败。失败后重试一次，仍失败就跳过，流水线和交叉验证会因此缺步骤。

**建议**：`turn.parse` 不为空时不追加这两句。可以用 LiteLLM 的 `response_format={"type": "json_object"}`（支持的模型才传）进一步降低风险。补一个测试：`parse` 不为空时，最后一条 user 消息不含"至少指出"。

### 3. 字数上限对结构化步骤太紧

`max_chars` 默认 300，`max_tokens` 由它换算成 450。交叉验证里一份互评要点评所有其他回答，裁判要同时写结论、共识和分歧，450 tokens 的 JSON 可能被截断，导致解析失败。建议结构化步骤用单独的、更宽松的 `max_tokens`（比如至少 1200）。

### 4. 小问题

- 假模型在交叉验证的回答阶段回复"（Claude 汇总）……"，"汇总"二字不对，看界面时容易误会。
- 第二批审查的第 2 条（`/api/models` 显示成员名、范围太窄）还没改。
